## 2. 데이터 스키마 꼬임 (⚠️ 모든 결과 페이지의 근본 원인)

**준기 증언**: "사주 정보가 이상하게 연결되어있어. 이용기록 데이터랑 사주팔자 정보가 뭐가 이상하게 꼬여있다."

**메모리 기록** (`project_storage_data_model.md`): 사주 정보 vs 이용기록 별도 테이블, cascade delete 금지.

### 추정 가능한 4가지 꼬임 시나리오

| 가설 | 증상 | 검증법 | 수정 방향 |
|---|---|---|---|
| **A. 단일 테이블 혼재** | `/storage`에서 사주 삭제 → 과거 결과도 사라짐 | Firestore Console `users/{uid}/profiles` 단일 경로인지 확인 | 분리: `users/{uid}/sajuProfiles` · `users/{uid}/resultHistory` 2개 |
| **B. profileId 누락** | 결과 페이지 진입 시 "어떤 사주인지" 모름 · 헤더 "변준기 · ..." 공란 | 결과 문서에 `profileId` 필드 존재 확인 | FK 추가 + 백필 스크립트 |
| **C. 자동저장 중복** | 같은 사주 결과가 N개씩 쌓임 (재진입마다 생성) | `resultHistory` count per profile | idempotency key `{profileId}_{contentType}_{YYYYMMDD}` |
| **D. 이용기록 cascade** | 보관함에서 사주 삭제 → 결제 내역·포인트도 영향 | `users/{uid}/rewardClaims` 와 profile 참조 관계 확인 | rewardClaims는 profileId 없이 uid만. 사주 삭제와 무관 |

### PC 즉시 점검 요청 (30분 내)

```bash
cd D:\550saju
# 1. Firestore 구조 확인
firebase firestore:delete --dry-run users/TEST_UID/profiles

# 2. 관련 코드 grep
grep -r "users/" src/firestore/ | head -30
grep -r "saveProfile\|saveResult" src/ | head -30

# 3. 실제 삭제 플로우 확인
grep -r "deleteProfile\|deleteDoc" src/pages/StoragePage.tsx
```

**결과 회신 포맷**:
- A/B/C/D 각각 해당/무관 판정
- 해당되면 현재 구조 스크린샷 1장 + 문제 함수 30줄
