# 사주500 — 로딩 UX 전면 개편 + 지연 단축 전략

> 목표: **체감 대기 시간 3초 이내 + 실제 완성 30~60초 = 이탈 없음**
> 원칙: 준기 우선순위 — 퀄리티 > 속도. warm 인스턴스 월 비용보다 **UX로 우회**.
> 작성: 2026-04-20 · 런칭 4-22 기준

---

## 0. 문제 정의 — 현재 AIProgressLoader의 한계

| 지점 | 현재 | 문제 |
|---|---|---|
| 결제 → 풀이 생성 | "풀이를 만들고 있어요" 1줄 텍스트 | 10~60초 대기 → 이탈 위험 |
| 로딩 동안 유저가 보는 것 | 스피너 + 단계 문구 4줄 순환 | **아무것도 안 일어나는 느낌** |
| 느낀 시간 vs 실제 시간 | 실제 30초 ≈ 체감 60~90초 | 체감이 2~3배 길게 느껴짐 |
| 네트워크 끊김 | 전체 중단 → 재결제 위험 | resume 불가 |
| 백그라운드 이탈 | 다시 돌아오면 처음부터 | 재생성 시 비용 2배 |

**결론:** 로딩은 "시간을 줄이는 문제"가 아니라 **"시간을 유저가 느끼지 못하게 하는 문제"**. 이틀 안에 잡아야 함.

## 1. 3티어 로딩 전략 (구간별 다른 UX)

콘텐츠 생성 시간이 다르므로 UX도 달라져야 함. **한 종류의 로딩 화면은 실패.**

### 1-1. Tier A · 즉시 (0~3초)
**대상:** 오늘의 운세 첫 단계, 꿈해몽 캐시 히트, 홈·입력·충전 페이지 전환
**전략:** **스켈레톤만**. 프로그레스 인디케이터 없음. 로딩 문구 없음.

```
[사주 미니카드]  ← 즉시 렌더 (실제 데이터 있음, 계산 빠름)
[━━━━━━━━━━] ← 스켈레톤 줄 3개 shimmer
[━━━━━━━━]
[━━━━━━]
```

- 1.5초 이내 로드되면 로딩 문구 안 뜸
- 프론트엔드 렌더 직후 백엔드 호출, 도착하면 부드러운 fade-in
- 스켈레톤이 "3초 뒤면 여기 채워진다"는 시각적 약속

### 1-2. Tier B · 짧은 대기 (3~10초)
**대상:** 오늘의 운세 전체, 주제별 심층 1운 (Sonnet 4.6), 꿈해몽 무료 Aha
**전략:** **스트리밍 + 섹션 단위 점진 노출**

```
SECTION 01 ✓ (100% done)  ← 먼저 나옴, 유저가 읽기 시작
SECTION 02 ✓ (100% done)
SECTION 03 ━━━━━━░░ (생성 중, 80%)
SECTION 04 [━━━] ← 스켈레톤
SECTION 05 [━━━]
```

- 첫 섹션이 도착하는 순간 **유저는 스크롤을 시작** → 체감 대기 시간 = 0
- 밑으로 읽어 내려가는 동안 뒷 섹션 완성
- 스크롤이 마지막 섹션에 도착할 때쯤 생성 완료

### 1-3. Tier C · 긴 대기 (10~60초)
**대상:** 프리미엄 종합 리포트 10운(Opus), 꿈해몽 심층 500원(Opus), PDF 생성
**전략:** **로딩 전용 풀스크린 + 단계 시각화 + 동적 한자 + 하단 로테이션 문구 (탈출구 없음)**

```
┌──────────────────────┐
│ ✦     ✦   ✦          │  ← 금빛 파티클 7종 drift/fade
│    [만다라 외·내]      │  ← 외부 CW 60s / 내부 CCW 50s
│    [진행 링 60%]      │  ← SVG stroke-dasharray, 단계별 채움
│       運              │  ← 한자 7색 그라데이션 스윕 + 호흡
│ ✦          ✦    ✦    │
│                      │
│  대운 10년 흐름을 맞추는 중 │  ← 5단계 라벨 (카피북 확정)
│  준기 님의 병오년 · 한 해 자리 │
│  ●●●○○ 3단계 / 전체 5단계    │
│                      │
│  [사주 상식]          │  ← 하단 로테이션, 3.6s 간격 18개
│  일간(日干)은 곧        │     사주 상식·격려·칭찬·일상
│  '나' 자신을 뜻합니다   │     카테고리 뱃지 + 격식체 본문
│                      │
│  정성껏 짓고 있습니다    │  ← 상태 캡션
└──────────────────────┘
```

- 4단계 이상이 **결정론적으로** 진행 (서버에서 단계 이벤트 emit)
- "알림으로 받기" / "백그라운드 전환" CTA **없음** — 완성까지 그 자리 대기가 기본 경험
- 지루함·불안을 탈출 버튼이 아닌 **콘텐츠(사주 상식·격려·칭찬·일상)** 와 **한자 다이내믹(링 채움 / 파티클 / 만다라 회전 / 그라데이션 스윕)** 으로 해소
- 60초 초과 시 에러로 간주 → 자동 환불 + 재시도 플로우 (5-3 참고)

## 2. 실제 지연 단축 — 서버·기술 전략

### 2-1. 🔥 스트리밍 (최우선)
**원리:** Anthropic API `stream: true` 옵션으로 token-by-token 수신.
- **첫 토큰 도착 시간(TTFT):** Opus 약 800ms, Sonnet 약 400ms, Haiku 약 200ms
- **전체 생성 시간(TTFD):** Opus 30~60s, Sonnet 10~30s, Haiku 5~15s
- **체감:** TTFT = 0.4~0.8초. 즉 **첫 글자가 1초 안에 나타남**.

**구현(PC):**
```typescript
// functions/src/content/premium/generate.ts
const stream = await anthropic.messages.stream({
  model: "claude-opus-4-6",
  max_tokens: 16000,
  system: SYSTEM_PROMPT,
  messages: [{ role: "user", content: userPrompt }],
});

// Firestore에 stub 문서 생성
const reportRef = db.collection("reports").doc(reportId);
await reportRef.set({ status: "streaming", sections: {}, createdAt: FieldValue.serverTimestamp() });

// 토큰마다 sections.XX 업데이트 (섹션 마크업 기반으로 청크 분리)
let buffer = "";
for await (const chunk of stream) {
  if (chunk.type === "content_block_delta") {
    buffer += chunk.delta.text;
    const section = parseSectionBoundary(buffer);
    if (section) {
      await reportRef.update({
        [`sections.${section.id}`]: section.content,
        status: "streaming",
        progress: section.index / TOTAL_SECTIONS,
      });
    }
  }
}
await reportRef.update({ status: "complete" });
```

**클라이언트(React):**
```tsx
const [report] = useDocumentData(doc(db, "reports", reportId));
// report.sections.01 부터 도착하는 대로 render, 없으면 skeleton
```

**예상 효과:** 체감 대기 시간 30~60초 → **1초 이내**.

---

### 2-2. 🔥 Prompt Caching (두 번째 우선)
**원리:** Anthropic `cache_control: { type: "ephemeral" }` — system prompt + 사주 기본 해석 컨텍스트를 **90% 할인가로 캐싱**. 5분 유지.
- 대상: 사주 원국·오행·십성·신살 베이스 설명 = 토큰 15~25K
- 캐시 히트율: 같은 유저 세션 내 70%+ 예상

**구현(PC):**
```typescript
const cachedSystem = [
  { type: "text", text: SAJU_FOUNDATION_CONTEXT, cache_control: { type: "ephemeral" } },
  { type: "text", text: USER_SAJU_BASE_ANALYSIS, cache_control: { type: "ephemeral" } },
];

await anthropic.messages.stream({
  model: "claude-opus-4-6",
  system: cachedSystem,  // array 형태로 cache 포인트 지정
  messages: [{ role: "user", content: topicSpecificPrompt }],
});
```

**예상 효과:**
- 입력 토큰 비용 90% 감소 → Opus 마진 3원 → 30원대 회복 가능성 (유닛이코노믹스 중대 변화)
- TTFT 추가 감소 20~30%

---

### 2-3. 🔥 병렬 섹션 생성
**원리:** 11섹션 리포트를 **1번의 긴 호출 vs 11번의 짧은 병렬 호출**.
- 1번의 긴 호출: Opus 60초 + 한 덩어리로 스트리밍
- 11번 병렬: Sonnet 10초 × 11개 동시 → 총 10초 (가장 느린 것 기준)

**예상:**
- 총 생성 시간 60s → **10~15s** (5~6배 빠름)
- 비용: 입력 토큰이 섹션마다 중복 → prompt caching으로 상쇄
- 품질 손실 위험: 섹션 간 일관성. 프리미엄은 Opus 1회 권장, 주제별 심층·꿈해몽 무료는 병렬 가능.

**권장 적용:**
- ✅ 주제별 심층(1운, Sonnet): 3~4섹션 병렬
- ✅ 꿈해몽 무료 Aha: 4~5섹션 병렬
- ✅ 오늘의 운세: 2섹션 병렬
- ❌ 프리미엄 10운(Opus): 단일 호출 유지 (일관성 우선)
- ❌ PDF: 콘텐츠는 이미 있음, 렌더만

### 2-4. Cloud Functions 콜드 스타트 완화
**현재:** 2nd gen, memory 1GiB, minInstances 미설정
**제약:** warm 비용 기각됨 (준기 결정 2026-04-19)

**대안 (돈 안 드는 것):**
- **Keep-alive ping** — Cloud Scheduler로 1분마다 `/health` 호출 → 인스턴스 유지
  - 비용: 매 invocation 과금 발생(월 $0.50~1) — warm 보다 훨씬 저렴
- **Lazy Puppeteer** — PDF 함수의 Chromium 로드를 **유저 요청 시작 시 prewarm** (생성 첫 단계에서 백그라운드 launch)
- **SDK preloading** — Anthropic SDK 초기화는 global scope로 (모듈 레벨 `new Anthropic()`)

**예상 효과:** 콜드 스타트 5초 → 1초 미만

### 2-5. 결과 캐싱 (Firestore)
**원리:** 동일 사주 + 동일 날짜 + 동일 주제 = 동일 결과. 재생성 금지.
- **오늘의 운세:** `users/{uid}/today/{YYYYMMDD}` — 같은 날 재접속 시 즉시 로드 (0ms)
- **주제별 심층 1운:** `users/{uid}/topics/{topicId}_{YYYYMMDD}` — 일자별 캐싱
- **프리미엄 10운:** `users/{uid}/premium/{reportId}` — 한 번 생성 후 영구
- **꿈해몽:** 유저 입력이 달라지므로 캐싱 불가, 생성마다 새로

**예상 효과:** 재방문 유저 Tier A(즉시) 진입. 첫 유저 외 로딩 제거.

## 3. 체감 시간 단축 — UX 전략

### 3-1. 🎨 Progressive Disclosure (점진 공개)
- **0초:** TopBar + 사주 미니카드 (계산 즉시, DB에 있음)
- **0.5초:** 스켈레톤 3줄 + shimmer
- **1초:** 첫 섹션 헤더 등장 (스트리밍 시작)
- **2초:** 첫 섹션 본문 등장
- **3~10초:** 사용자가 읽는 동안 뒷 섹션 생성
- **완료:** 마지막 섹션에서 "풀이가 완성됐습니다" 토스트 (카피북)

### 3-2. 🎨 Optimistic UI
- 결제 성공 버튼 → 1초 내 결과 페이지로 전환 (미리 결제 검증)
- 결과 페이지는 **스켈레톤 먼저, 콘텐츠 fade-in**
- 유저가 "기다리는 화면을 본 적이 없다"고 느껴야 함

### 3-3. 🎨 단계 감각 (결정론적 5단계)
Tier C 프리미엄 로딩:
```
1. 사주 원국을 읽는 중          ● ● ○ ○ ○
2. 오행과 신살을 정돈하는 중      ● ● ● ○ ○
3. 대운 10년 흐름을 맞추는 중     ● ● ● ● ○
4. 올해 기운과 잇는 중            ● ● ● ● ●
5. 정성 풀이로 다듬는 중          ✓
```
- **서버에서 단계 이벤트 emit** (추상 스피너가 아닌 실제 단계)
- Firestore: `progress: { step: 3, total: 5, label: "..." }`
- 클라이언트: realtime 구독, 단계 변할 때마다 애니메이션

### 3-4. 🎨 브랜드 몰입 — 동적 한자 스테이지 (Tier C 전용)
단일 한자(命·運·易) 정적 표기가 아니라 **5층 레이어 구조**로 "AI 같지 않은 프리미엄"을 완성:

| 층 | 요소 | 스펙 |
|---|---|---|
| L0 | 후광(halo) | radial gradient(#F0E8D9 → transparent), 3.4s ease-in-out breathe |
| L1 | 외부 만다라 | 삼중 동심원, rotate CW 60s linear |
| L2 | 내부 만다라 | conic-gradient 빗살(12등분), rotate CCW 50s, radial mask로 링 형태 |
| L3 | 진행 링 | SVG `<circle>` stroke-dasharray, 단계별 stroke-dashoffset 채움, linearGradient(F0E8D9→B8965A→5C4A2E) + drop-shadow |
| L4 | 금빛 파티클 | 7개 4px 점, radial gradient + box-shadow 글로우, drift1/2/3 키프레임 각기 다른 지연 |
| L5 | 한자 본체 | Noto Serif KR 900 · 140px · 9색 135deg 그라데이션 · background-size 320% · sweep 4.5s + breathe 3s |

- **단계 전환 시 한자 교체** 허용: 원국(命) → 오행(五) → 대운(運) → 연운(年) → 완성(筆)
- **금지:** 단순 rotation spinner, 원형 progress 바 단독, generic 로딩 점 애니메이션 — 전부 "AI 티"

### 3-5. 🎨 진행바 아래 로테이션 문구 (탈출구 CTA의 대체재)
유저가 "탈출하고 싶다" 감정을 느끼기 전에 **콘텐츠로 몰입도를 유지**한다.

**배치:** 진행바(step-track/step-count) **바로 아래 중앙**. `margin-top:34px` 정도의 여유. 하단 bottom 고정 아님 — 진행바와 문구가 시각적으로 한 그룹으로 묶이게.

**구조:** 카테고리 뱃지 없음. 본문 한 줄(또는 두 줄)만. Noto Serif KR 12.5px 500 #5C4A2E.
```
일간(日干)은 태양을 뜻합니다. 내 기운의 본체이자 세상을 마주하는 얼굴입니다.
```

**50개 초기 풀 (카테고리 4군 섞어 운영 — 유저에게는 노출 X):**
- **사주 진짜 지식 20개** — 일간·천간지지·대운세운·용신·격국·십신·신살 등 깊이 있는 개념
- **실용 꿀팁 10개** — 계약 타이밍, 이사 방향, 색상·방향 보완, 절기, 공망일 활용 등 생활 접점
- **관점 전환·지혜 10개** — "사주는 사용설명서", "없는 글자는 탐하지 않아도 되는 영역" 류의 사색
- **격려·몰입 10개** — "풀이는 예언이 아닙니다", "선택은 당신의 몫", 프리미엄 대기 톤

**스타일 규칙:**
- 격식체 100% (됩니다·입니다·습니다) — 프리미엄 대기 화면은 격식체 비중 상향
- 금지 표현: "분석 중", "잠시만", "곧 완료", "가능성이 있", "~수 있어요" (면피체)
- 금지 카테고리: 뻔한 격려("힘내세요"), AI 자의식("제가 열심히 읽고 있어요")
- 문장 길이 22~50자. 두 호흡 문장 허용 (예: "사주는 사용설명서입니다. 쓰는 사람에 따라 결과가 다릅니다.")
- 회차 풀 확장은 정기 업데이트 (월 1회 5~10개 추가) — 런칭 후 유저 피드백 반영
- 전체 풀은 `사주500_UI개편_목업_로딩_v1.html` Tier C의 `#tipRotator` 참고

**교체 주기:** 3.6s. 50개 순환 = 3분이면 한 바퀴. 60초 최장 대기 시 유저는 약 16개 문구 노출.

**기술 구현:**
- 클라이언트 setInterval(3600). document.querySelectorAll로 로드 후 active 클래스 토글
- fade 0.7s ease (opacity + translateY 6→0)
- 런타임에 배열 가져오기: `const tips = await getDoc(doc(db, "content", "loadingTips"))` — 어드민이 풀 갱신 가능

## 5. 에러·복구·재시도

### 5-1. 네트워크 끊김
- Firestore offline persistence 켜져 있으므로 재연결 시 자동 resume
- 스트리밍 중 끊기면 서버는 계속 생성, 유저는 다음 재접속 시 `status: "complete"` 확인
- 클라이언트: 5초 이상 업데이트 없음 → "연결이 끊겼습니다. 잠시 후 다시 시도해주세요" (카피북)

### 5-2. API 에러
- Anthropic 429 rate limit: exponential backoff (1s, 2s, 4s, 8s, 실패 시 fallback 모델)
- Anthropic 500/overloaded: 즉시 Sonnet fallback (프리미엄도 Sonnet으로, 유저에게 노출 없음)
- 완전 실패: 전액 환불 + "풀이를 만들지 못했습니다. 금액은 청구되지 않습니다"

### 5-3. 60초 초과 (에러 취급)
- **정의:** 60초 넘게 `status: "streaming"` 유지 = Anthropic API 비정상 지연 or 서버 실패로 간주
- **동작:**
  1. 클라이언트: 60초 타이머 만료 시 화면 전환 → "풀이 생성이 지연되고 있습니다. 재시도하시겠습니까?"
  2. [재시도] 버튼 누르면 동일 입력으로 재요청 (기존 reportId와 별개 id, 중복 과금 방지)
  3. 재시도도 60초 초과하면 "풀이를 만들지 못했습니다. 금액은 청구되지 않습니다" + 자동 환불 트리거
- **주의:** "알림으로 받기 / 백그라운드 전환" 플로우는 **없음** — 유저는 그 자리에서 기다리거나 재시도하거나 환불받는 3지선다
