## 2. 오너 작업 방식 (가장 자주 지적된 것부터)

1. **요청은 하나도 빠뜨리지 않는다.** 여러 항목을 말하면 표로 만들어 하나씩 체크하고, 직접 대조한 뒤 보고한다. "무시당한 것 같다", "다 반영 안 됐잖아"가 4월부터 10월까지 가장 많이 반복된 불만이다.
2. **"됐다"는 직접 확인한 뒤에만.** 프롬프트가 실제로 들어갔는지, 연동과 화면까지 확인한다. 직접 본 것만 '확인했다'고 하고 나머지는 '확인 못 함'으로 적는다. 측정 안 한 속도나 효과로 약속하지 않는다. 보고에는 어디까지 갔는지(목업, 코드, 커밋, 서버 배포, .ait 업로드) 단계를 붙인다.
3. **화면은 직접 본다.** "화면을 못 본다"는 말 금지. 캡처와 DOM 측정으로 확인한다. 결과물과 미리보기는 오너가 찾지 않게 직접 열어 보여준다.
4. **스스로 판단해서 끝까지.** "알아서 해"는 그 범위 안에서 바로 실행. 주관적 품질("AI 같지 않나요?")을 오너에게 되묻지 않고 브랜드 기준으로 직접 감사한다. 결정이 필요한 것만 추천안과 함께 묶어서 묻는다. 판단 기준은 마케터, 데이터 아키텍트, 실제 고객 관점.
5. **질문에는 설명으로 답한다.** "그게 뭐냐"고 물으면 설명부터. 묻지 않은 비활성화나 삭제로 답하지 않는다. 보고에서 전문용어를 피한다(보일러플레이트, 박멸, 크리티컬 회귀 같은 말을 오너가 매번 되물었음).
6. **회귀 금지.** 다른 작업을 하다 이전에 확정한 수정을 덮으면 크게 화낸다. 옛 디자인과 옛 코드가 다시 튀어나오면 안 된다.
7. **삭제는 신중하게, 버릴 것은 완전히.** 지운 뒤 중요한 걸 날리지 않았는지 반드시 확인. 나중에 살릴 기능은 꺼 두고, 버릴 기능은 방어 코드로 남기지 말고 완전히 삭제한다.
8. **CLI 와 배포는 Claude 가.** functions 배포, firestore rules, 빌드는 Claude 가 한다. .ait 콘솔 업로드와 토스 콘솔 작업, 실카드 결제는 오너 몫. 웹 hosting 은 배포하지 않는다(10-03 이후). 오너에게 할 일은 우선순위대로 짧게.
9. **퀄리티 다운그레이드 절대 금지, 그러나 속도와 원가도 본다.** "생성시간 2배면 CS 도 2배", "원가는 정확히 파악하되 퀄리티는 그대로". 무료 콘텐츠(오늘의 운세, 꿈해몽)도 최고 품질이다.
10. **대화와 보고는 전부 한국어, 가운뎃점 금지, 이모지 금지.** 결론과 행동을 먼저("그래서 뭐 어카자고"). 콘솔 클릭 안내만 단계식으로 친절하게.
11. **테스트성 생성 호출을 남발하지 않는다**(비용). 필요한 만큼만.
12. **데이터 사고 조사는 읽기 전용.** 원인 확정 전 DELETE, UPDATE, 덮어쓰기, 마이그레이션 금지. 쓰기 전 백업과 위치 알림, dry-run.
13. **벤치마킹은 겉 디자인보다 사업 전체**(BM, 전환 구조, 지식). 레퍼런스는 참고만 하고 콘텐츠마다 우리만의 특색.
14. **큰 디자인 작업은 목업 먼저, 그대로 구현.** 카피라이팅도 같이 본다.

## 4. 콘텐츠와 명리학

### 4-1. 근거와 정확성
- 모든 결과는 명리학 이론 근거. AI 가 점수를 찍게 하지 않는다. 주제 점수는 서버 `computeTopicBaseScore` 가 결정론으로 산출하고 AI 는 그 점수를 그대로 쓴다. 점수 분포를 처방하는 문구(중심값 65 등)를 프롬프트에 다시 넣지 않는다.
- 점수는 너무 후하지도 짜지도 않게. 낮은 점수에 기분 상할 수 있으니 이유와 대비법을 같이.
- 같은 사주는 언제 봐도 같은 결과, 같은 점수, 같은 신살. 콘텐츠끼리 모순 금지: 종합사주 '주제별 한눈에' 점수 = 해당 주제운 점수, 월운의 주제 점수 = 주제운 점수, 행운 색과 방위는 원국 용신 하나에서.
- **만세력 절대 룰**: 간지는 계산한 값만 쓴다. AI 에게 간지를 추론시키지 않는다. 상대방 사주는 서버가 lunar 로 계산해 주입한다. 사주대화에서 제3자 생년월일이 나와도 간지를 지어내지 않는다. (6/11 실사례: 1995-06-06 戊辰일이 AI 추론으로 壬午 출력)
- 두 사람 콘텐츠는 양방향 대칭: 합, 충, 원진 같은 객관 판정은 A 가 보든 B 가 보든 같고, 서사는 의뢰인 본인 시선.
- 사주 사실(귀인, 시진, 월건 15개월, 일진의 용신 판정 등)은 모델이 계산하지 않고 서버가 표로 준다(`functions/src/ai/sajuFacts.ts`).
- 사용자가 쓰지 않은 사실을 지어내지 않는다. 꿈해몽에서 사용자는 '물과 바다'만 썼는데 수평선과 파도 소리를 지어낸 사례. 재회운에서 상대 정보가 없는데 상대 사주를 창작한 사례.
- 풀이는 입력된 사주만 근거로 한다. 대화 속 개인 맥락으로 개인화하지 않는다.
- 진태양시: KST -30분 고정, 시 경계는 시계 :30, 3:30 = 인시. 서머타임 1948~51, 1955~60, 1987, 1988. 출생지는 입력받지 않는다. 학파마다 갈리는 부분은 줏대 있게 밀되 안내 문구.

### 4-2. 서술 원칙
- 출력은 일상어. 원전과 학자 출처 언급 0건. 한자는 첫 등장에 괄호 풀이, 섹션당 2~3개. 무료 콘텐츠는 일상어 100%(명리 용어 괄호 보조 섹션당 2개 이하).
- 괄호 풀이를 달아도 생극 구조 서술("지지에 金 두 개 깔고", "토생금")은 어렵다. 비유 없이 일상 결과로 푼다. 시적 비유("겨울 한복판에 태어난 태양")는 '외계어'다.
- 단호하게, 그러나 명령조나 공격적이지 않게("무당처럼 단호하게, 그렇다고 공격하라는 뜻은 아님"). 면피 어미(~할 수 있어요, ~하기 쉬워요, ~하는 편이에요) 금지. 무내용 단정 금지: [사주 근거] + [무엇이] + [언제/어떻게].
- 같은 말 반복 금지, 섹션끼리와 콘텐츠끼리 내용 중복 금지. 사람마다 다르게(100명이면 100개). 같은 일주끼리 정적인 부분은 같아도 된다.
- 요약 한 줄은 부정어로 끝내지 않는다. 나쁜 결과는 대비법과 함께, 위기를 기회로 바꾸는 쪽으로. 흉몽이면 해석과 극복법과 조심할 점까지.
- 부정 예측만 다루는 단독 섹션 금지(예: 권태기 시점 예측). 결혼 적기는 두 사주가 좋은 연도로만. 너무 가까운 시기 못박기와 수십 년 뒤 같은 먼 미래 모두 피한다.
- 사주를 모르는 사람이 실행할 수 없는 조언 금지("계수 기운 가진 사람을 만나라").
- 가족 구성과 연애 여부를 가정하지 않는다(부모, 형제, 자녀, 연인이 없는 사람도 있음). 성별 호칭은 시댁/처가, 모르면 배우자 가족, 양가.
- 제목이 약속한 내용은 반드시 채운다. 비어 있으면 채우거나, 빼거나, 각색한다. 상황과 맞지 않는 제목 금지(솔로인데 '현재 연인과 결혼할 확률', 첫 취준인데 '이직' 섹션).
- 주제 범위를 넘는 섹션 금지(10주제 경계표 TOPIC_BOUNDARIES). 주제마다 흐름과 구성이 달라야 한다("연애운 보고 결혼운 보면 500원 날린 느낌이 들면 안 됨").
- 해석 금기: 죽음과 수명, 이혼과 사별 단정, 질병명(소화기 계통 수준으로), 전생과 부적과 굿, '살이 끼었다', 공망은 '비어 있음 = 잠재력', 재혼과 자녀 수 단정, 타인 비교, 유명인 사주 단정.
- 재회운은 솔직하게: 사주상 어려우면 어렵다고 하고, 가능하면 이유를 확실히. 이별한 사람이 위로받고 "내 얘기구나" 할 만큼 깊게.
- 재물운 유형은 다양하게(사업형, 안정 수입형, 노년 발복형 등). 직업운은 '어떤 직업이 왜 맞는지'이지 면접, 합격, 이직이 아니다.
- 꿈해몽은 꿈, 사주, 고민이 설득력 있게 이어져야 한다("그냥 갖다붙인 느낌" 금지). 첫 문장은 길몽/흉몽 판정.
- 오늘의 운세는 보는 시간대에 따라 멘트가 조금 달라야 한다(새벽, 점심, 저녁).
- 프롬프트는 길지 않게, 금지 출력은 확실히 막게. 프롬프트의 예시 문장은 ✓든 ❌든 모델이 복사하므로 내용 없는 OO 패턴으로만. 어조 점검은 user 메시지 맨 끝(TONE_FINAL_CHECK).

## 8. 결제, 잔액, 데이터

- 앱 = 토스 IAP, 웹 = 포트원(KG이니시스). 토스페이먼츠는 쓰지 않는다. (CLAUDE.md 의 토스페이먼츠 서술은 낡음)
